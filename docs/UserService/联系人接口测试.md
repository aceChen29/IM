# 联系人接口测试（本地种子数据）

本文对应当前 `ContactController`、`AuthorizeFilter` 和 2026-10-30 写入的本地测试数据。先启动 MySQL、Redis、Kafka、Nacos 和 UserService。以下请求直接发到 UserService：`http://localhost:8104`。

## Header 与鉴权

| 访问方式 | Header | 当前行为 |
|---|---|---|
| 直连 UserService `:8104` | JSON 请求设置 `Content-Type: application/json`；其他请求无需特殊 Header | `ContactController` 当前没有读取或校验 Token。下面的示例可直接测试。 |
| 走 Gateway `:10010` | `Access-Token: <登录返回的 accessToken>`；`Refresh-Token` 可带但不是每次必须；JSON 请求再加 `Content-Type: application/json` | 网关验证 Access-Token 的 JWT 和 Redis 中的值。Access-Token 无效时，合法 Refresh-Token 只会让网关返回“令牌已过期”，不会直接放行。**当前网关没有 `/api/contact/**` 路由，因此这些接口现在不能通过网关访问。** |

这里使用的 Header 名称是 `Access-Token` 和 `Refresh-Token`，不是 `Authorization: Bearer ...`。即使将来添加网关路由，当前实现也没有核对 Token 中的用户 ID 与路径里的 `{userId}` 是否一致；测试时请使用自己账号的 ID，正式使用前需要补上这一鉴权校验。

## 测试数据与顺序

| 代号 | 用户 ID | 初始关系 |
|---|---|---|
| A | `930000000000000001` | 主测试用户 |
| B | `930000000000000002` | A 的好友，单聊 `930000000000001001` |
| C | `930000000000000003` | A 的好友，单聊 `930000000000001002` |
| D | `930000000000000004` | 向 A 发了未读申请 |
| E | `930000000000000005` | 向 A 发了未读申请 |
| F | `930000000000000006` | 向 A 发了未读申请 |
| H | `930000000000000008` | A 的好友，单聊 `930000000000001003` |

先查未读数量和申请列表，再通过 D、拒绝 E、标记 F 已读。拉黑 B 后可以查看详情中的 `status=1`，取消拉黑后恢复为 `0`。最后删除 C；此操作会删除双方好友关系及共同单聊会话。本文的初始预期以这组数据尚未被操作、尚未过期为前提。三条申请已登记过期任务，约在 **2026-10-31 00:14（北京时间）** 到期；到期处理或重复执行修改接口后，结果会不同。

以下成功响应的 HTTP 状态通常为 `200`，统一外层为 `{"code":200,"data":...,"message":"ok"}`。下文只在动态字段处使用占位值。

## 1. 获取未读好友申请数量

```http
GET http://localhost:8104/api/contact/930000000000000001/applyCount
```

Query 参数：无。Body：无。Header：直连时无特殊要求。

初始预期：

```json
{"code":200,"data":{"count":3},"message":"ok"}
```

通过 D、拒绝 E、标记 F 已读后，再查 A 的未读数应为 `0`。

## 2. 获取好友申请列表

```http
GET http://localhost:8104/api/contact/930000000000000001/apply?pageNum=1&pageSize=20
```

Query 参数：`pageNum=1` 为第一页，`pageSize=20` 为每页 20 条。Body：无。Header：直连时无特殊要求。

初始预期：`data.total=3`，`data.list` 包含 D、E、F；三条记录初始 `status=0`，`isReceiver=1` 表示 A 是申请接收者。三条记录同批写入，**列表先后顺序不要作为断言**。示例中的时间是动态值：

```json
{
  "code": 200,
  "data": {
    "list": [
      {"userId":"930000000000000004","nickname":"Contact Dan","avatar":null,"msg":"你好，我是 Dan，可以加好友吗？","status":0,"time":"<数据库中的更新时间>","isReceiver":1},
      {"userId":"930000000000000005","nickname":"Contact Ella","avatar":null,"msg":"你好，我是 Ella，可以加好友吗？","status":0,"time":"<数据库中的更新时间>","isReceiver":1},
      {"userId":"930000000000000006","nickname":"Contact Finn","avatar":null,"msg":"你好，我是 Finn，可以加好友吗？","status":0,"time":"<数据库中的更新时间>","isReceiver":1}
    ],
    "total": 3,
    "pageSize": 20,
    "pageNum": 1,
    "pages": 1,
    "hasNext": false,
    "hasPrevious": false
  },
  "message": "ok"
}
```

该接口同时查询当前用户发出和收到的申请；后续如果 A 自己发了申请，`total` 会增加。

## 3. 通过 D 的申请

```http
POST http://localhost:8104/api/contact/930000000000000001/application/1
Content-Type: application/json
```

路径参数：`userId=A`，`status=1` 表示通过。Body：

```json
{"receiveuserIds":["930000000000000004"]}
```

`receiveuserIds` 是当前 DTO 的字段名，**实际要填申请发送者 D 的 ID**。通过和拒绝每次只能传一个 ID。预期响应中的单聊 `sessionId` 是运行时生成的雪花 ID：

```json
{
  "code": 200,
  "data": {
    "userId": "930000000000000004",
    "sessionId": "<新生成的单聊会话 ID>",
    "sessionType": 0,
    "sessionName": "Contact Dan",
    "avatar": null
  },
  "message": "ok"
}
```

随后 D 的申请状态为 `1`；A 与 D 各新增一条好友记录和 `user_session` 记录，共用同一个新会话 ID。重复通过同一申请不会再次成功。

## 4. 拒绝 E 的申请

```http
POST http://localhost:8104/api/contact/930000000000000001/application/2
Content-Type: application/json
```

路径参数：`userId=A`，`status=2` 表示拒绝。Body：

```json
{"receiveuserIds":["930000000000000005"]}
```

预期：

```json
{"code":200,"data":true,"message":"ok"}
```

随后 E 的申请状态为 `2`，不会建立好友关系或会话。

## 5. 标记 F 的申请已读

```http
POST http://localhost:8104/api/contact/930000000000000001/application/3
Content-Type: application/json
```

路径参数：`userId=A`，`status=3` 表示已读。Body：

```json
{"receiveuserIds":["930000000000000006"]}
```

预期：

```json
{"code":200,"data":true,"message":"ok"}
```

随后 F 的申请状态为 `3`，仍未建立好友关系；重复对已读申请执行“标记已读”会失败，因为该实现只更新 `UNREAD` 记录。

## 6. 拉黑好友 B

```http
POST http://localhost:8104/api/contact/930000000000000001/block/930000000000000002
```

路径参数：`userId=A`，`receiveuserId=B`。Query 参数：无。Body：无。Header：直连时无特殊要求。

预期：

```json
{"code":200,"data":true,"message":"ok"}
```

仅 A → B 的 `friend.status` 变为 `1`；B → A 的状态仍为 `0`。

## 7. 取消拉黑好友 B

```http
DELETE http://localhost:8104/api/contact/930000000000000001/block/930000000000000002
```

路径参数：`userId=A`，`receiveuserId=B`。Query 参数：无。Body：无。Header：直连时无特殊要求。**先执行第 6 步。**

预期：

```json
{"code":200,"data":true,"message":"ok"}
```

随后 A → B 的 `friend.status` 恢复为 `0`。未拉黑时直接调用本接口会返回业务错误。

## 8. 获取好友详情 B

```http
GET http://localhost:8104/api/contact/930000000000000001/friend/930000000000000002
```

路径参数：`userId=A`，`friendId=B`。Query 参数：无。Body：无。Header：直连时无特殊要求。

初始状态或完成第 7 步后的预期：

```json
{
  "code": 200,
  "data": {
    "userId": "930000000000000002",
    "nickname": "Contact Bob",
    "avatar": null,
    "email": "im.contact.bob@example.test",
    "phone": "13993000002",
    "signature": "拉黑和取消拉黑测试",
    "gender": 1,
    "sessionId": "930000000000001001",
    "status": 0
  },
  "message": "ok"
}
```

如果在第 6 步之后、第 7 步之前查询，`status` 应为 `1`；会话 ID 不变。

## 9. 删除好友 C

```http
DELETE http://localhost:8104/api/contact/930000000000000001/friend/930000000000000003
```

路径参数：`userId=A`，`receiveuserId=C`。Query 参数：无。Body：无。Header：直连时无特殊要求。

预期：

```json
{"code":200,"data":true,"message":"ok"}
```

随后 A → C、C → A 的好友关系被删除，共同的单聊会话 `930000000000001002` 及双方的 `user_session` 记录也被清理。此接口用于专门准备的测试关系；执行后重复删除会返回“好友关系不存在”。

## 结果与当前数据不同怎么办

- `count`、申请状态或好友数量不同：先检查是否已经执行过上述修改操作，或申请是否已到期。
- 直连 `:8104` 返回连接失败：确认 UserService 已启动。
- 网关 `:10010` 返回 `401` 或找不到路由：这是当前过滤器和缺少 `/api/contact/**` 路由的行为，不能通过同时携带两个 Token 解决。
- 雪花 ID 在请求 JSON 中始终写为字符串，避免 JavaScript 数字精度丢失。
